# 招募：1–2 小时，帮 macOS 的 OpenGL 从 4.1 往上推

## 一句话

苹果的 OpenGL 停在 4.1 已经十几年，几何着色器（GS）在 macOS 的 GL 上**从来没有存在过**——所以吃 GS 的光影包、吃 compute 的模组，在 Mac 上没有一条能走的路。

现在这条链已经通了：`GL → Zink → KosmicKrisp → Metal 4`。GS 在 10 月底进了 Mesa 主线，transform feedback（XFB）还差最后一个待评审 MR。剩下的事不是设计，是**没人把这三样东西在同一台机器上对齐过一次**。

我需要几台 M 系机器，跑一次 1–2 小时的验证，把日志贴回去。

## 现在到底到哪一步了（别被"GL 4.6"骗了）

网上说的 GL 4.6 有三种，混着说会得出完全错误的结论：

| 构建 | 是什么 | GS | XFB | 报的 GL 上限 |
|---|---|---|---|---|
| A | SDK 1.4.363.1 / Homebrew Mesa 26.3.1 | ✗ | ✗ | 2.1 |
| B | Mesa main 自编译（含 `14f59d06`） | ✓ | ✗ | 2.1 |
| B+ | B 再叠 !44928 | ✓ | ✓ | 3.3（作者口径，待复核） |
| C | main + 第三方补丁集 | ✓ | ✓ | 4.6（有 CTS 记录） |

**这次要测的是 B+。** 它是第一个理论上能越过 3.0 的公开组合，而这一档目前零实机数据。B 只作对照：只多一个 GS 位、没有 XFB，版本应该原地不动——正好验证「3.0 先卡 XFB」这个判断。

顺带一条，免得误会：如果你用 HMCL，它确实能切 KK 后端——但那个开关只做 Vulkan 的三件事（选 ICD、换 Vulkan loader、传 `--graphicsBackend vulkan`）。它能证明「KK 能跑 MC」，不能证明「GL 4.6 可用」。列表里的 `Mesa Zink` 在 macOS 上是可见但空操作，选了会静默回落到苹果 GL。协议第 7 节写了为什么。

## 需要你做什么

1. 一台 Apple Silicon Mac，macOS 26 或 27，能装 Xcode 命令行工具
2. 照着这份协议跑一遍：`02_test_protocol_zh.md`（1–2 小时，复制命令，不需要写代码）
3. 把 `vulkaninfo` 的 JSON、算出来的 GL 版本、missing 列表贴到 MR 或仓库 issue

**核心步骤不需要启动游戏。** 工具直接从驱动能力表算出 GL 天花板，跑不跑 MC 都行。

## 优先要哪几台

按价值排序，不是按机型新旧：

1. **M1 / M2 + macOS 26** —— KosmicKrisp 官方文档点名说这一档在暴露新扩展时问题最多，也是最需要零回归证据的配置。目前公开记录里恰好是空的。
2. **M5 / M6 + macOS 27** —— 已经有一个 float16 的 CTS 失败样本，需要确认是不是新机型通病。
3. 其它 M 系 + macOS 26/27 —— 也算数，只是不解决最关键的空白。

## 说清楚这不是什么

- **不是一个能日常用的驱动。** 关了终端就回去了，不要拿它当默认 GL。
- **不保证能玩。** 已知问题包括灰屏、黑闪帧、二次启动崩、部分光影编译失败。协议里都列了。
- **不收个人数据。** 只要机型、macOS 版本、构建标识、`vulkaninfo` 和能力差集。贴之前把用户名和绝对路径删掉。

## 你会得到什么

一份公开的、可复现的数据，署名归你。如果这条链最终能被上游接住，这份日志就是"它在真机上跑过"的第一个证据。

对这个项目来说，一份**失败**的日志和一份成功的一样有用——现在缺的不是好消息，是有人真的跑过一次。
